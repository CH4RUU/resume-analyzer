# Resume Analyzer

A full-stack resume scoring tool built with Java 17, Spring Boot 4, Spring Data JPA and MySQL.
Upload a resume (PDF, DOCX or TXT), optionally paste a job description, and get an instant score
breakdown, matched/missing skills, and improvement suggestions — plus an opt-in AI-generated
narrative review via Google Gemini.

**Live demo:** [resume-analyzer-oil5.onrender.com](https://resume-analyzer-oil5.onrender.com)
(hosted on Render's free tier — the first request after a period of inactivity can take
30-60 seconds while the instance wakes up)

## What it does

1. You upload a resume file and, optionally, paste a job description.
2. The server extracts plain text from the file (PDF/DOCX/TXT), scores it across five
   dimensions, and returns matched/missing skills plus plain-English suggestions —
   all synchronously, all free, all deterministic.
3. Optionally, you can also ask for **AI feedback**: a natural-language review generated by
   Google Gemini, layered on top of the same scoring data (strongest points, weaknesses,
   concrete edits).
4. Every analysis is persisted to MySQL, so a history list and past results survive restarts.

## Stack

- **Backend:** Java 17, Spring Boot 4 (Web, Data JPA, Validation)
- **Database:** MySQL (`mysql-connector-j`) in production, H2 in-memory for tests
- **Text extraction:** Apache PDFBox (PDF), Apache POI (DOCX)
- **Optional AI:** Google Gemini API (`gemini-2.5-flash` by default) via Spring's `RestClient`
- **Frontend:** plain HTML/CSS/JS (`src/main/resources/static`) served directly by Spring Boot
  — no separate build step, no Node toolchain
- **Deployment:** Docker (multi-stage build), Render (compute) + Clever Cloud (MySQL)

## Architecture

```
                     ┌─────────────────────────────────────────────┐
                     │              Spring Boot app                │
                     │                                              │
 Browser  ──HTTP──▶  │  AnalysisController (REST, /api/analyses)    │
 (static              │        │                                    │
  HTML/JS)             │        ▼                                    │
                     │  AnalysisService (orchestration + tx)        │
                     │   │        │              │                  │
                     │   ▼        ▼              ▼                  │
                     │ TextExtractor  ResumeAnalyzer  GeminiFeedbackService
                     │ (PDFBox/POI)   (rule-based       (optional, calls
                     │                 scoring engine,   generativelanguage
                     │                 SkillCatalog)     googleapis.com)
                     │        │                                      │
                     │        ▼                                      │
                     │  AnalysisRepository (Spring Data JPA)         │
                     └────────────┬──────────────────────────────────┘
                                  │
                                  ▼
                          MySQL (`analysis` table +
                          element-collection tables for
                          skills/suggestions)
```

**Request flow for a scored upload (`POST /api/analyses`):**

1. `AnalysisController` receives the multipart file + optional job description text.
2. `AnalysisService.analyzeAndStore` calls `TextExtractor` to pull raw text out of the file
   (PDFBox for PDF, POI for DOCX, plain read for TXT/MD).
3. `ResumeAnalyzer` runs the actual scoring: it asks `SkillCatalog` (a hand-curated,
   regex-backed skill vocabulary) which skills appear in the resume and, if a job description
   was given, which skills appear there too. Keyword, section, contact-info, impact, and format
   sub-scores are computed independently and combined into a weighted overall score.
4. The resulting `Analysis` entity (scores, matched/missing skills, suggestions, raw resume
   text) is persisted via `AnalysisRepository` and returned as JSON.

**Request flow for AI feedback (`POST /api/analyses/{id}/ai-feedback`)** is a separate,
explicit call — it's not bundled into the main analyze request, since it costs an external API
call and (for most providers) money. It loads the stored `Analysis`, builds a prompt from the
resume text + job description + already-computed scores, sends it to Gemini, and persists the
response text back onto the same row.

## Design decisions & trade-offs

- **Rule-based scoring as the core, AI as a layer on top, not a replacement.** The five
  sub-scores (keywords, sections, contact info, impact, format) are all regex/heuristic-driven —
  no model call, no API key, no per-request cost, fully deterministic and unit-testable. AI
  feedback is bolted on as an optional endpoint precisely so the core product doesn't depend on
  an external service staying up, priced favorably, or configured at all. This is why the two
  are separate endpoints instead of one endpoint with a "use AI" flag.

- **Gemini over Claude for the optional AI layer.** Anthropic's API is pay-per-token from the
  first request with no ongoing free tier; Gemini has a genuinely free tier for `gemini-2.5-flash`.
  Since this feature is explicitly opt-in and cost-sensitive, free-by-default won out over
  higher output quality. The provider is isolated behind `GeminiFeedbackService` — swapping
  providers again would mean rewriting one class, not touching the controller, DTOs, or entity.

- **Plain HTML/CSS/JS frontend instead of React/Vite.** The requested stack was backend-only
  (Java/Spring/MySQL); adding a Node build pipeline for a single-page form + results view would
  have been overhead without a corresponding benefit. Serving static files directly from
  `src/main/resources/static` also means the whole app is one deployable artifact — one Docker
  image, one Render service, one thing to keep alive.

- **MySQL over Postgres for the free-hosted deployment.** Render's own free managed database is
  Postgres-only and free instances expire after a fixed window; MySQL was requested and Clever
  Cloud offers a MySQL add-on that's free indefinitely (not a trial), so the deployment story
  stayed consistent with local development instead of silently swapping engines for hosting
  convenience.

- **`@Lob` + explicit `columnDefinition = "LONGTEXT"` for resume text and AI feedback.**
  Hibernate's default mapping for a `String` field annotated `@Lob` on MySQL doesn't reliably
  produce a `LONGTEXT` column — it can land on a much smaller type depending on dialect
  inference. Since resume text can be several KB and AI feedback responses aren't bounded by the
  app, the column type is pinned explicitly rather than left to inference (see
  [Challenges](#challenges-along-the-way) below — this was actually hit, not just anticipated).

- **Env-var-driven config, not profile-specific properties files.** `application.properties`
  reads `${SPRING_DATASOURCE_URL:<local-default>}` style placeholders rather than a separate
  `application-prod.properties`. One file, one set of defaults for local dev, and production
  just overrides via environment variables — no active-profile flag to remember to set on the
  host.

## Challenges along the way

These are the actual problems hit while building and deploying this, not hypothetical ones:

- **Spring Initializr version confusion.** The Initializr metadata endpoint reported a Spring
  Boot version as `4.0.7.RELEASE`, but that artifact doesn't exist on Maven Central — the real
  coordinate is `4.0.7` (Spring Boot dropped the `.RELEASE` suffix from version strings years
  ago; the metadata endpoint's naming was misleading). Fixed by checking Maven Central's
  `maven-metadata.xml` directly for the real version list.

- **`RestClient.Builder` isn't auto-configured** in this project's dependency set (no
  `spring-boot-starter-webmvc`-provided auto-configuration for it here), so injecting
  `RestClient.Builder` into `GeminiFeedbackService`'s constructor failed at startup with
  `NoSuchBeanDefinitionException`. Fixed by building the `RestClient` directly with
  `RestClient.builder()` inside the service instead of relying on an injected builder bean.

- **MySQL `Data too long for column 'resume_text'`.** Once real resume text started flowing
  through the pipeline, inserts started failing — Hibernate had mapped the `@Lob String` field to
  a column too small to hold it. Fixed by adding `columnDefinition = "LONGTEXT"` explicitly and
  recreating the schema (the existing `ddl-auto=update` table didn't get its column type widened
  automatically, since Hibernate's `update` mode is conservative about altering existing columns).

- **Local MySQL setup went three rounds.** A MySQL download in `~/Downloads` turned out to be a
  **client-only** package (no `mysqld` binary at all, despite being 386MB) — traced by grepping
  the whole extracted tree for `mysqld` and finding only client tools. Then `brew install mysql`
  failed because `formulae.brew.sh` (Homebrew's package index) was unreachable from this
  environment, while Maven Central and GHCR were fine — a sandboxed-network quirk, not a Homebrew
  bug. The fix that actually worked: pulling the real MySQL server tarball directly from
  `cdn.mysql.com` (reachable) and running `mysqld` from it manually. That server then collided on
  port 3306 with a **pre-existing system MySQL LaunchDaemon** already running on this Mac whose
  root password was unknown — resetting it would've needed `sudo`, which needs a password I don't
  have. Rather than touch someone else's running service blind, the new instance was just run on
  port 3307 instead, leaving the existing one alone entirely.

- **Gemini's free tier quietly excludes some models.** After wiring up Gemini and deploying, the
  AI feedback endpoint returned a `429` with `limit: 0` specifically for `gemini-2.0-flash` —
  the model was configured correctly and the API key worked, but that particular model's free
  tier quota had been set to zero (superseded by newer models). Fixed by switching the default to
  `gemini-2.5-flash` and exposing the model name as an independently overridable `GEMINI_MODEL`
  env var, so a future quota change doesn't require a code change or redeploy, just an env var
  edit.

- **A transient `404` on the deployed homepage right after a push.** Immediately after pushing
  the Gemini swap, the live Render URL briefly 404'd on `/` while the API endpoints under
  `/api/**` kept returning `200` — almost certainly Render's edge routing mid-swap between the
  old and new container during a rolling deploy. It resolved itself within seconds on retry;
  called out here because it looked alarming from the outside (site "down") while the underlying
  service was actually healthy the whole time.

## Running locally

### Prerequisites

- JDK 17
- A MySQL server (or point `application.properties` at one you already have)

### Configure the database

Edit `src/main/resources/application.properties` if your MySQL credentials differ, or override
via environment variables (`SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`,
`SPRING_DATASOURCE_PASSWORD`) without touching the file:

```properties
spring.datasource.url=jdbc:mysql://localhost:3307/resume_analyzer?createDatabaseIfNotExist=true&useSSL=false&allowPublicKeyRetrieval=true
spring.datasource.username=root
spring.datasource.password=password
```

The database and its tables are created automatically on startup
(`spring.jpa.hibernate.ddl-auto=update`).

### Run

```bash
./mvnw spring-boot:run
```

Then open **http://localhost:8080**.

### Optional AI feedback locally

```bash
export GEMINI_API_KEY=...   # free key from https://aistudio.google.com/apikey
./mvnw spring-boot:run
```

Without the key set, `POST /api/analyses/{id}/ai-feedback` returns `503 Service Unavailable`
with a clear message — everything else works identically either way. Model is configurable via
`GEMINI_MODEL` (defaults to `gemini-2.5-flash`).

## Running tests

Tests use an in-memory H2 database, so no MySQL connection is needed:

```bash
./mvnw test
```

## API

| Method | Path                              | Description                                                                                          |
|--------|-----------------------------------|--------------------------------------------------------------------------------------------------------|
| POST   | `/api/analyses`                   | Multipart upload: `resume` file + `jobDescription` (optional)                                          |
| GET    | `/api/analyses`                   | List past analyses (most recent first)                                                                 |
| GET    | `/api/analyses/{id}`              | Get one analysis in full detail                                                                        |
| DELETE | `/api/analyses/{id}`              | Delete an analysis                                                                                      |
| POST   | `/api/analyses/{id}/ai-feedback`  | Generate AI feedback via Gemini (needs `GEMINI_API_KEY`); form param `jobDescription` (optional)         |

## Deploying for free

The app is containerized (`Dockerfile`) and reads all datasource/API-key config from environment
variables, so it runs on any Docker host without code changes. This deployment uses two free
services: **Render** (runs the container) and **Clever Cloud** (hosts the MySQL database) — both
have a free tier that doesn't expire and doesn't require a credit card.

### 1. Push this repo to GitHub

Render deploys straight from a GitHub repo.

### 2. Create a free MySQL database on Clever Cloud

1. Sign up at [clever-cloud.com](https://www.clever-cloud.com/) (free, no card required).
2. Create a new application → **Add-on** → **MySQL** → pick the free **DEV** plan.
3. Once provisioned, open the add-on's "Information" tab and copy the host, port, database name,
   user, and password.

### 3. Create a free Web Service on Render

1. Sign up at [render.com](https://render.com/) and connect your GitHub account.
2. **New +** → **Blueprint**, point it at this repo — it picks up `render.yaml` automatically
   and creates a free Docker web service.
   (Alternatively: **New +** → **Web Service** → select the repo → runtime **Docker**.)
3. In the service's **Environment** tab, set:
   - `SPRING_DATASOURCE_URL` = `jdbc:mysql://<clever-cloud-host>:<port>/<db-name>?useSSL=false&allowPublicKeyRetrieval=true`
   - `SPRING_DATASOURCE_USERNAME` = the Clever Cloud MySQL user
   - `SPRING_DATASOURCE_PASSWORD` = the Clever Cloud MySQL password
   - `GEMINI_API_KEY` = (optional) your free Gemini key from [Google AI Studio](https://aistudio.google.com/apikey), only if you want the AI feedback endpoint live
4. Deploy. Render builds the `Dockerfile` and starts the container; `PORT` is injected
   automatically and the app already binds to it (`server.port=${PORT:8080}`).

### Free-tier caveats

- Render's free web service **spins down after ~15 minutes of inactivity** — the first request
  after idling takes 30-60s to wake back up.
- Clever Cloud's free MySQL "DEV" plan has limited storage (a few hundred MB) — plenty for resume
  text and scores, not meant for heavy production traffic.
- Gemini's free tier has per-model, per-minute, and per-day request limits that change over time
  (see [Challenges](#challenges-along-the-way)) — if AI feedback starts returning `429`s, check
  which models currently carry a free quota and update `GEMINI_MODEL` accordingly.
- If either provider changes its free-tier terms, the same `Dockerfile` and env-var-driven config
  work unmodified on Railway, Fly.io, or any other container host — only the environment
  variables need to be set on the new platform.
